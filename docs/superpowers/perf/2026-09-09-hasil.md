# Hasil pengukuran setelah upgrade visual

Tanggal: 9 September 2026
Commit kode: `7d1adbc`
Pasangan dari: `2026-09-08-baseline.md`

## Cara ukur yang dipakai sekarang

Lighthouse dengan `--throttling-method=simulate` memberi angka LCP yang tidak
cocok dengan perilaku nyata di halaman ini: ia melaporkan jarak LCP−FCP sekitar
4 detik padahal elemen LCP-nya h1 yang dirender server dan tergambar bersamaan
dengan FCP. Simulasinya menghitung ulang antrean unduhan dari graf permintaan,
dan hasilnya melebih-lebihkan penundaan pada halaman yang isi terbesarnya sudah
ada di HTML.

Angka di bawah karena itu diambil dengan emulasi jaringan dan CPU sungguhan lewat
Chrome DevTools Protocol di Playwright: Slow 4G (1,6 Mbps, latensi 150 ms) dan CPU
4× lebih lambat, viewport 390×844. LCP dibaca dari `PerformanceObserver`, jadi
elemen penyebabnya ikut tercatat.

Server lokal mengirim gzip (`/tmp/gzserve.py`), karena `python3 -m http.server`
tidak mengompresi apa pun dan itu sendiri menggeser FCP lebih dari satu detik.

CLS 0 di semua halaman, tidak berubah dari baseline. TBT median Lighthouse
homepage 44–71 ms (baseline 49 ms).

## Sisa yang belum ditutup

`components/shared/AnimatedSection.tsx` masih memakai pola yang sama dengan hero
lama: `initial={{ opacity: 0 }}` sampai React selesai hydrate. Itu sebabnya
halaman legal masih punya jarak 1.036 ms. Komponen itu dipakai 18 file di luar
scope pekerjaan ini — blog, halaman produk, detail studi kasus — jadi tidak
disentuh. Menggantinya dengan animasi CSS yang bertitik awal terlihat akan
menutup sisa jarak di semua halaman itu sekaligus.

## Ukuran aset yang ditambahkan

setelah `load`, dan tidak sama sekali kalau pengguna minta gerak dikurangi atau
menyalakan penghemat data. Poster hero 16.694 / 11.326 B. Empat gambar PageHero
41.396–81.400 B untuk desktop dan 16.640–36.164 B untuk strip mobile.
